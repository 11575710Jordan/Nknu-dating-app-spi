7\n\n--- PAGE 8 ---\n負載(Load)測試
• 負載(Load)測試為一種效能測試。
• 測試電腦、周邊設備、伺服器、網路的規格工作限制，藉以找出元件的
限制、瓶頸或錯誤。
• 提供使用者瞭解，在固定的性能下，最多可以同時執行多少工作、程序或應
用程式。分為兩種情況
• Longevity testing: 評估系統在長時間中的一般工作負載。
• Volume testing: 評估系統在限制的時間內高負載情況。
• 在實驗室控制環境下比較不同系統的能力，或精確量測單一系統的能力，或
量測系統在真實世界的功能理想值。
• 從網路上下載大量的檔案。
• 在一台電腦、或伺服器上同時執行多個應用程式。
• 給予伺服器大量的EMAIL。
• 從硬碟持續的存取資料。
• 測試具有高速處理器卻有限的RAM
8\n\n--- PAGE 9 ---\n• 一種效能測試。測試在極端工作負載，仍然能正常工作的情況。
• 測試電腦、網路、程式、設備在不適當的狀態下仍具有一定的效用。
• 量化評估：量測系統錯誤的頻率或在甚麼情況、甚麼時間當機。
• 質性評估：測試是否可以抵擋denial-of-service (DoS)攻擊。
• 測試必須控制在一個不利的執行環境，直到系統當機或性能低於一
定程度，包括
• 在一台電腦同時執行許多高資源要求的應用程式
• 使用大量的垃圾郵件侵襲伺服器
• 針對一個網站同時製造大量的服務要求 
• 嘗試使用病毒、木馬、間諜程式感染系統
壓力(Stress)測試
9\n\n--- PAGE 10 ---\n負載測試 vs. 壓力測試
• 負載測試
• 使用預先定義的負載等級來評估系統效能
• 在一般條件或者預定的條件下，測量一個系統需要花多長的時間執行各
種程式、任務以及功能
• 壓力測試
• 評估一個系統在超出其能力範圍時產生的反應
• 效能測試是為了在不同的負載等級下判定系統效能
10\n\n--- PAGE 11 ---\n壓力測試的重要
• 假設網站目前的資訊處理量為一天300,000筆
• 300,000/(24*60*60) = 3.47 transactions per second (TPS)
• 市場調查使用者可接受的回應時間
• <4 sec：可接受
• 4-8 sec：30% 取消資訊處理
• 8-10 sec：60% 取消資訊處理
• >10 sec：90% 取消資訊處理
• 預期將增加25%-75%的資訊處理量
• 假設每一筆資料傳輸是$1元
• 基於"讀取資訊的回應時間"，這間公司將面臨每天潛在的損失約$112,500 ~ $472,500
• 300,000*1.25*0.3 = 112,500 
• 300,000*1.75*0.9 = 472,500

• 連接時間 (Connection time)
• 所需時間為客戶端與伺服器端建立連結的時間
• 在網路所花費的時間
• 傳送時間 (Send time)
• 所需時間為客戶端傳送資料到伺服器的時間
• 在網路所花費的時間
• 接收時間 (Receive time)
• 所需時間為伺服器傳送回應到客戶端所需的時間
• 在網路所花費的時間
16\n\n--- PAGE 17 ---\n效能測試術語 (續)
• 回應時間 (Response time)
• 所需時間為完成一個特定的傳輸所需的時間
• 在伺服器所花費的時間
• 交易時間 (Transaction time)
• 所需的時間為客戶端處理接收到的資料的時間
• 完成傳輸在網路、客戶端、伺服器上所花費的所有時間總和
• 每個工具供應商使用稍有不同的術語來描述相同的概念
• 哪個術語才是正確的並不重要
17\n\n--- PAGE 18 ---\n效能衡量標準
• 每秒傳輸量 (Transaction per second, TPS)
• 每秒伺服器處理的資料傳輸 (T/sec)
• 每秒要求數 (Hit per second, Hit/sec)
• 吞吐量 (Throughput)
• 在一段給定的時間內可以處理多少、多大量的”工作"？
• 伺服器處理的資料量 (KB/sec)
• 回應時間 (Response time)
• 使用者需要等待多久的時間？
• 不同使用案例下所花費的時間？
• 使用者的數量 (Number of users)
• 特別是網站
• 同步回應時間 (Simultaneous Response time)
• 註冊的資料庫大小 (Registered Database size) 18\n\n--- PAGE 19 ---\n效能衡量標準 (續)
• 並行連線 (Concurrent connections)
• 並行開啟連結的數量

20\n\n--- PAGE 21 ---\n效能測試的種類
• 有效性測試 (Availability testing)：系統或元件正常運行，沒有當機
時間的百分比
• 基準測試 (Baseline Testing)：將新的伺服器與已知的參考標準比較，
例如現存的軟體或量測數據
• 失效點 (Breakpoint)：增加負載直到系統失效。或在限制的測試環
境下，盡可能增加負載直到系統失效
• 元件角度 (Component-Specific)：檢測系統元件的效能和強健度，
可在元件完成後執行。
• 校驗 (Calibration)：檢測系統是否符合政府法規授權訂定需求。
• 能力測試 (Capacity testing)：系統未使用的能力，或可以支援額外
工作的能力。
• 達成目標型測試 (Goal-reaching test)：設定一個負載目標門檻，
當達成時，停止測試並蒐集數據、分析結果。例如 response time 
超過10秒。
21\n\n--- PAGE 22 ---\n效能測試的種類 (續)
• 長時間測試 (Duration or Endurance or Longevity Testing)：在測試
實驗室日夜(24x7)操作系統，偵測長時期執行的錯誤，如slow 
memory leaks；或重複持續增加系統存取交易一段時間，找出問題。
• 死結測試 (Deadlock testing)：執行容量測試，偵測系統是否有資源
競爭，例如多個要求者嘗試存取相同的資料庫；由於資料庫記錄鎖住
造成衝突，引起系統鎖住使用者要求。
• 降級作業模式 (Degraded Mode of Operation)：測試當並非所有資
源都在工作時，是否系統仍然提供/降低期望的服務等級，例如在一個
有多餘應用程式伺服器的伺服器群組中，嘗試關閉其中一個伺服器，
讓系統仍然能夠繼續操作。
• 錯誤率測量 (Error rate measurement)：當系統在正常或高負載的情
況，功能或特性的錯誤率。若使用者無法正確完成任務，快速反應與
高處理速度都沒用。 22\n\n--- PAGE 23 ---\n效能測試的種類 (續)
• 熱點 (Hot Spot)：在一個系統特定限定的部分，著重於高負載，以
偵測系統的脆弱點。
• 負載變化 (Load Variation)：測試不同負載以反應真實使用負載的
典型樣式和一段時間資料流情形。
• 負載測試 (Load Testing)：放入真實系統執行時的資料量以測試服
務等級，如反應時間等
• 網路測試 (Network Testing)：找出可以量測系統負載的策略網路點、
連網設備的數量等等。
• 峰值測試 (Peak test)：在尖峰時期的負載，例如股票交易系統在一
開始和結束時。
• Ramp-Up：測量啟始程序的時間，例如一個閒置的網路設備，當需
要工作時，必須在50 milliseconds啟動。
• 資源運用度 (Resource utilization)：系統資源運用的程度。
23\n\n--- PAGE 24 ---\n效能測試的種類 (續)
• 規模 (Scalability)：系統成長的能力，包括增加每一位使用者的
工作負載、並行使用者的數量、資料庫大小。
• 激盪測試 (Spike Testing)：突然增加許多並行的使用者登入系統，
以測定伺服器行為。在很短時間，針對工作負載，決定系統如何
處理意外增加的需求。系統是否能針對快速有意義的改變做出反
應，重導資源使用，例如透過負載平衡。
• Standard Benchmark：當難以辨識系統真實使用情形，則使用
標準的工作負載，而非特定使用者的工作負載。
• 壓力測試 (Stress Testing)：測試最大量使用者或存取交易的負載，
直到系統當機的點
• 根據使用情況 (Usage-Based)：根據作業情況，模擬真實環境的
操作測試。
• 大量測試 (Volume Testing)：處理大量的資料的測試。
24\n\n--- PAGE 25 ---\n效能測試的種類 (續)
• 壓力測試 (Stress Testing)
– 網站逐漸加壓，目的是確保原先成功運作的功能仍正確運作，但更應注重網
站所有功能完整性(functional integrity)。例如某網站能提供某股票獲利百分
比，但當該網站被加壓時，應確保該網站仍能正確計算各種股票獲利百分比。
– 資料完整性(data integrity)是任何交易網站重要特性之一。當超過負載時，
網站會發生什麼情況？其影響會隨所處環境而異，可能輕微也可能是災難性
的。
– 壓力測試可防止潛在災難性危險情況，尤其透過負載平衡主機(load balancer)
或資料複製伺服器(data replication server)改善網站性能時，實施壓力測試
常能找到無法預期的問題。
– 執行壓力測試的測試案例必需包含可能會發生的所有衝突，網站管理者需瞭
解若某衝突發生，要採取的動作。
– 壓力測試的交易通常包含需要大量計算、或較為重要的資料處理工作，設法
達到較有效率顯示網站資源耗用之表徵。測試案例需包含有關資料庫系統的
增加、修改、刪除等作業，以對資料庫網站實施輸入、輸出及例行性服務項
目等的壓力。
25\n\n--- PAGE 26 ---\n效能測試的種類 (續)
• Spike test
– 預測網站什麼時候會遭遇像暴風雨之類的大災難，這種預測
是否正確？什麼時候會發生？從那裡發生？災難有多嚴重？
傷害的程度？
– 電子商務網站，假日時段、頭號電腦病毒、特殊號外新聞、
有關產品優惠消息都可能成為激盪事件。
– 激盪測試也被稱為超負載測試(overload test)、浸蝕測試
(soak test)或浪濤測試(surge test)。
– 另一種變化是彈跳測試(bounce/elasticity testing)，將激
盪負載之大小稍作調整，在適當範圍內上下彈跳，以觀察某
一網站是否能適應負載變化、及是否能自行控制資源運用，
需要資源時能提出要求，不用時能立即釋放，達到資源運用
的最佳效益。
26\n\n--- PAGE 27 ---\n效能測試的種類 (續)
• 激盪測試的執行，是由超出正常平均值的大量隨機需求驅
動，讓網站在非常短時間內經歷異乎尋常的負載成長。
• 網站能適應負載逐漸增強變化，但突襲性激盪事件有可能引起相
當嚴重問題。
• 例如樂透網站通常會在使用者下注後經歷一波浪濤洶湧，有些網
站無法處理這種浪濤式負載，造成網站當機；因此能預估某些激
盪事件，則可針對此事件腳本設計測試案例，透過激盪測試檢查
分析網站調適能力。
• 美國股市行情即時網站，經過歷史資料分析發現，最有可

29\n\n--- PAGE 30 ---\nMemory Leak
• Memory Leak (記憶體漏洩)：記憶體的使用量隨著時間慢慢增加直到消
耗殆盡。
• Memory Leak造成原因：某個被配置的記憶體無法再被參照，也無法被
釋放；無法被系統再使用。
• 作業系統或Application Server實體記憶體使用圖，若隨時間增加，記憶
體使用量呈現明顯增加趨勢，程式極有潛在此問題。
– Java程式，一個宣告static 的Array A儲存已開啟的視窗JFrame物件 。若使用者開啟
一個視窗W1，W1會被存入Array A中，當W1關閉，沒有把W1從Array A移除，雖
然W1被指到null，Garbage Collector卻不會回收W1。因為Array A仍保有W1參照，
GC假設W1之後有被使用的機會，所以沒有回收W1。若程式持續開關大量視窗，它
所用記憶體會呈現增加趨勢，造成典型Memory Leak狀況。
• 解決的方式，在W1關閉時同時把W1從Array A裡移除即可。

44\n\n--- PAGE 45 ---\nWorkload Model
Workload Model 描述系統實際會承受什麼樣的負載，而不只是指定一
個使用者數量。
應包含：
• Arrival Rate：每秒到達的請求或交易數。
• Concurrent Users：同時執行中的使用者數。
• Transaction Mix：不同 API 或業務交易的比例。
• Think Time：使用者操作間隔。
• Payload Size：Request / Response 大小。
• Data Volume：資料庫資料量及資料分布。
• Ramp-up / Ramp-down：負載增加與降低方式。
