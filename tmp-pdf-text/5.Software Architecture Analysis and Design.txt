• Software Architecture typically refers to the bigger 
structures of a software system, and it deals with how 
multiple software processes cooperate to carry out their 
tasks.
• Software Design refers to the smaller structures and it deals 
with the internal design of a single software process.

• The software architecture of a program or computing 
system is the structures of the system, which comprise 
• software components, 
• the externally visible properties of those components, and 
• the relationships among them. 
[L. Bass, P . Clements, R. Kazman, Software Architecture in Practice, Addisdon-Wesley, 1998. ]
• IEEE 1471–2000
• an architecture is "the fundamental organization of a system 
embodied in its components, their relationships to each other, 
and to the environment, and the principles guiding its design 
and evolution."

\n\n--- PAGE 26 ---\nServerless Architecture
• a cloud computing design pattern where developers only need to 
write and execute code
• underlying server maintenance, resource configuration, and automatic scaling 
are entirely handled by cloud service providers (such as AWS, Google Cloud, 
and Microsoft Azure).
• No Server Management Required: servers and operating systems are 
completely abstracted. Developers don't need to manually maintain hardware 
or patch system security updates.
• Event-Driven: The code doesn't run continuously; it only starts executing when 
triggered by specific events (such as HTTP requests, file uploads to buckets, or 
database changes).
• Pay-Per-Use: Billing is based entirely on the actual computation time and 
number of times the code is executed. 
• Auto-Scaling: The system automatically scales from zero to thousands of 
instances as traffic increases, and automatically scales down as traffic 
decreases.

37\n\n--- PAGE 38 ---\nArchitecture: 
a set of important design decisions
• Architecture is not simply a block diagram or a folder structure.
• Architectural decisions constrain subsequent implementation 
and impact quality attributes.
• Architecture needs to explain the rationale: 
• why the partitioning is done this way
• why communication is done this way
• why deployment is done this way.
• Undocumented decisions typically become future technical debt.

(subsystems) : a server-side Web Application, a Single-Page

84\n\n--- PAGE 85 ---\nArchitecture Smell vs Code Smell
85
Code Smell Architecture Smell
過長 method 模組邊界不清楚
重複程式碼 多個服務重複持有同一資料規則
不清楚的命名 domain concept 沒有被建模

缺少單元測試 系統缺少可測試的切分與隔離

93\n\n--- PAGE 94 ---\nAI 產生架構建議的常見風險
94
把大型企業架構套用到小型系統，造成 over-engineering。
忽略團隊能力、部署環境、預算與時程。
將 microservices、event-driven、RAG、agent 等名詞堆疊，但缺
少取捨。
未處理 data privacy、prompt injection、fallback 與
observability。
沒有 evidence，只是生成「看起來合理」的敘述。
94\n\n--- PAGE 95 ---\n驗證 AI 架構建議的檢查表
95
每個 component 是否有明確責任？
每條 dependency 是否有必要？方向是否合理？
每個 quality attribute 是否有對應 tactic？
是否存在不可驗證的主張？
是否有說明風險、限制與替代方案？
是否能用小型 prototype 驗證關鍵假設？

99\n\n--- PAGE 100 ---\nSummary
100
• The core shift from coding to architecture is from "can the 
functionality be changed?" to "can the structure support 
quality?"
• AI can accelerate observation, classification, and alternatives 
generation.
• The architect's job remains judging evidence, risks, trade-
offs, and making decisions.
