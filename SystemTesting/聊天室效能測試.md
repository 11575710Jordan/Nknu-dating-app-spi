# 商業化交友 App - 聊天室效能測試與 Workload Model 規劃

本文件依據目前 `chat/` 目錄實作，規劃聊天室收件匣、訊息、AI 建議、共同行事曆與語音頁面的工作負載及效能測試方式。現況是純前端 Demo：訊息與行程寫入瀏覽器 `localStorage`，AI 建議以本機規則產生，麥克風由瀏覽器 MediaDevices API 控制；目前沒有聊天 API、伺服器資料庫、WebSocket 或遠端語音連線。因此，以下伺服器 TPS、頻寬與集中式儲存量是未來後端容量規劃的估算，並非目前系統實測結果。

---

## 一、業務情境與假設指標設定 (Business Assumptions)

1. **目標用戶規模**：以月活躍用戶 (MAU) 50,000 人估算，假設每位活躍用戶每日傳送 20 則訊息，則每日訊息量為 50,000 × 20 = 1,000,000 則。
2. **作業時間分佈**：假設 40% 的每日訊息集中於晚間 3 小時高峰期間。
3. **並行互動量**：容量規劃以尖峰時 2,000～3,000 組對話同時使用作為目標情境；這是規劃假設，並非目前前端 Demo 的連線數。
4. **訊息酬載假設**：平均 30 個中文字約 0.1 KB；使用者 ID、對話 ID、時間戳記等 metadata 約 0.4 KB，單則訊息請求約 0.5 KB。
5. **保存紀錄大小假設**：包含訊息文字、發送者與時間等欄位，單筆序列化紀錄估計約 0.7 KB；實際大小依文字長度及 JSON 欄位而異。

---

## 二、流量與到達率估算 (Arrival Rate / TPS)

* **每日平均訊息量**：
  * 50,000 人 × 20 則／人／天 = 1,000,000 則／天。
  * 平均到達率 = 1,000,000 ÷ 86,400 ≈ **11.57 則／秒**。
* **晚間尖峰訊息量**：
  * 1,000,000 × 40% = 400,000 則集中於 3 小時。
  * 尖峰到達率 = 400,000 ÷ (3 × 3,600) ≈ **37.04 則／秒**。
* **活動期壓力情境**：以尖峰 1.5～2 倍估算，約 **55～74 則／秒**。

以上把每則訊息視為未來後端的一筆送出交易。現有 `ChatStore.send()` 是同步更新本機資料，沒有網路請求，因此目前沒有可量測的伺服器 TPS。

---

## 三、頻寬需求估算 (Bandwidth Estimates)

* **訊息送出尖峰頻寬**：37.04 則／秒 × 0.5 KB ≈ **18.52 KB/s**，約 **0.148 Mbps**（只計算請求端訊息酬載）。
* **交易組合規劃**：若未來採用 API，初步可依下列比例產生壓測工作負載；此比例用於規劃，不代表目前已有這些 API。
  1. 開啟收件匣、載入對話與未讀狀態：15%。
  2. 讀取對話、標示已讀：15%。
  3. 傳送訊息：55%。
  4. 取得 AI 聊天建議或破冰話題：8%。
  5. 讀取或新增共同行程：5%。
  6. 語音工作階段控制／訊號交換：2%（未來項目；目前沒有遠端語音服務）。
* `ChatAI` 目前只在瀏覽器執行關鍵字與模擬個人資料比對；`ChatSchedule` 只讀寫本機儲存；`getUserMedia()` 只開啟本機麥克風。這三項目前不產生伺服器端請求流量。

---

## 四、儲存空間需求估算 (Storage Estimates)

* **未來後端集中保存訊息的估算**：
  * 1,000,000 則／天 × 30 天 × 0.7 KB ≈ **21,000,000 KB，約 21 GB／月**。
  * 若全量訊息保留 6 個月，約 **126 GB**，尚未包含索引、備份、複寫及其他資料表空間。
* **目前瀏覽器端單一使用者估算**：
  * 20 則／天 × 0.7 KB × 180 天 ≈ **2.52 MB／人／半年**，僅計算訊息紀錄，不含行程、個人資料及瀏覽器儲存格式額外成本。
  * 現有 `ChatStore.save()` 每次送出都序列化並寫入整份對話資料；對話愈長，序列化及儲存成本愈高，應列為長對話效能測項。
* 行事曆範本與新增行程另存於 `nknu-chat-schedule-v1`；語音頁不保存或上傳音訊。各瀏覽器的實際儲存配額與清除政策不同，需在目標瀏覽器測試。

---

## 五、前端效能測試規劃 (Client Performance Test Plan)

以下是建議驗收門檻，尚未實測；測試時應記錄瀏覽器、作業系統、裝置規格、對話數、訊息數及 localStorage 資料大小。

| 測試情境 | 測試資料／操作 | 建議效能指標 |
|---|---|---|
| 聊天室首次載入 | 首次建立 Mock 對話並繪製收件匣 | DOM 可操作時間 ≤ 2 秒；無未處理 JavaScript 錯誤 |
| 對話清單擴增 | 50、200、500 段對話，測排序、未讀數與列表繪製 | 收件匣更新 ≤ 500 ms |
| 長對話讀取 | 單一對話分別載入 100、1,000、5,000 則訊息 | 點選至訊息可操作 ≤ 1 秒；記錄繪製時間及記憶體；確認長對話不造成頁面凍結 |
| 訊息送出與持久化 | 短訊息、500 字上限訊息，重複送出並重新載入 | 輸入到畫面更新 ≤ 200 ms；記錄 `localStorage` 寫入時間及失敗情況 |
| 收件匣搜尋 | 200、500 段對話中輸入名稱或訊息關鍵字 | 輸入反應 ≤ 100 ms；確認清單結果正確 |
| AI 建議 | 有訊息、無收到訊息及不同關鍵字情境 | 建議面板開啟 ≤ 200 ms；確認最多顯示 3 筆且不阻塞輸入 |
| 共同行事曆 | 首次產生 3 筆範本、重複開啟、逐筆新增行程 | 面板更新 ≤ 200 ms；重開頁面後行程仍存在且按對話區隔 |
| 麥克風開關 | 支援／不支援裝置、允許／拒絕權限、離開頁面 | 分別記錄權限回應時間；確認關閉或離頁後音訊軌道停止，不把使用者權限等待時間算成頁面渲染延遲 |
| 儲存空間壓力 | 增加大量訊息直至 `localStorage` 寫入失敗 | 確認錯誤可被提示、頁面仍可操作，並記錄資料量與寫入延遲 |

## 六、Workload Model 總結規格表

* **Arrival Rate（訊息到達率）**：平均約 11.57 則／秒；晚間尖峰約 37.04 則／秒；活動期規劃約 55～74 則／秒。
* **Concurrent Users（並行使用量）**：規劃 2,000～3,000 組同時互動對話；前端測試另以不同對話與訊息資料量檢驗瀏覽器渲染能力。
* **Transaction Mix（未來 API 工作負載）**：收件匣 15%、讀取對話／標示已讀 15%、送出訊息 55%、AI 建議 8%、行事曆 5%、語音控制 2%。現況為純前端，不存在對應 API。
* **Payload Size（酬載大小）**：每則訊息請求估計 0.5 KB；訊息保存紀錄估計 0.7 KB。
* **Bandwidth（尖峰請求頻寬）**：以訊息送出估算約 18.52 KB/s（0.148 Mbps），不含回應、協定標頭、TLS、重試及媒體串流。
* **Storage（集中式訊息儲存）**：估計約 21 GB／月、保留 6 個月約 126 GB；目前則由每位使用者的瀏覽器分別保存資料。
* **Think Time（使用者思考時間）**：假設輸入訊息間隔約 5～15 秒；語音權限請求須另行量測，不視為一般頁面運算時間。
* **測試狀態**：本文件提供工作負載估算與測試計畫，數值為規劃假設；目前未執行 50,000 使用者或伺服器端壓力測試。
